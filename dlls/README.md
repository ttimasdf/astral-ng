# Windows DLL bundle

This directory contains prebuilt Windows x64 runtime files that are copied next
to `astral.exe` for Windows builds.

Direct consumers in this repository:

- `windows/runner/CMakeLists.txt` copies all DLLs except `Packet.lib` into the
  Flutter Windows runner output after each build.
- `.github/workflows/ci.yml` copies `dlls/*` into
  `build/windows/x64/runner/Release/` before creating the Windows zip artifact.
- The Inno Setup script generated by `.github/workflows/ci.yml` currently
  packages `*.dll` and `data/*` only. That means `Packet.lib` and
  `WinDivert64.sys` are present in the zip artifact but are not included in the
  setup artifact unless the installer script is changed.

EasyTier itself also ships architecture-specific copies of `Packet.dll`,
`Packet.lib`, `wintun.dll`, and `WinDivert*.sys` under
`rust/easytier/easytier/third_party/`. The Rust build uses that submodule copy
for link search paths via `rust/build.rs` and EasyTier's own `build.rs`. This
top-level directory is the Flutter application packaging mirror for the x64
Windows app.

## `Ak.dll` analysis

`Ak.dll` is the only file in this directory that is not obviously part of
EasyTier, Wintun, Npcap/WinPcap, WinDivert, or the Microsoft VC runtime. It is
also not passive: because it exports `DllMain`, Windows will execute it whenever
a process loads the DLL.

Evidence from Binary Ninja/static analysis:

- The DLL is x86-64 Rust code built from `src\\lib.rs` on a machine/user path
  containing `C:\Users\baika\...`.
- `DllMain` handles process attach (`DLL_PROCESS_ATTACH`) and reads `kl.toml`
  from the DLL/executable directory.
- Embedded TOML/serde field names define this apparent config shape:
  `rule_groups`, each with `name`, `regex`, and `rules`; each rule has `op`,
  `match_ip`, `match_port`, `replace_ip`, `replace_port`, `bind_nic`,
  `enable_auto_nic`, and `nic_name_filter`.
- It calls `EnumWindows`, `GetWindowThreadProcessId`, `IsWindowVisible`, and
  `GetWindowTextW` to obtain the current process' visible window title, then
  matches that title against rule-group regexes.
- It installs detours for Winsock functions `connect`, `bind`, `sendto`, and
  `recvfrom`. The replacement functions log original targets/sources and call
  the original Winsock functions afterward.
- It calls `GetAdaptersInfo` when binding rules are active, apparently to choose
  a NIC by name/filter or by local IP.
- It sends internal log/status messages over UDP to `127.0.0.1:9999` (port
  `0x270f`) with Chinese messages such as `[配置] 解析成功`, `[连接] 原始目标`,
  `[绑定] 原始`, `[网卡绑定] 成功绑定到`, `[UDP发送] 原始目标`, and `[UDP接收] 来源`.

Likely intended purpose:

- A game/application network shim or proxy helper loaded into another Windows
  process to redirect selected socket connections, rewrite IP/port pairs, and
  force socket binds through a chosen network adapter.
- It is probably controlled by an adjacent `kl.toml` file and a local UDP log UI
  or controller listening on `127.0.0.1:9999`.

Potential effects on a target system/process if loaded:

- Alters outbound connection destinations for matching rules.
- Alters `sendto` targets for UDP traffic.
- Alters or forces `bind` behavior, including binding sockets to a local NIC/IP.
- Enumerates visible windows and reads window titles for rule selection.
- Enumerates network adapters and their IP/name data.
- Emits local UDP telemetry/logging to `127.0.0.1:9999`.
- Installs inline/API hooks in the loading process, which can destabilize apps,
  trigger anti-cheat/EDR heuristics, or conflict with other hook libraries.

Online lookup notes:

- Searches for the SHA-256, `Ak.dll`, `kl.toml`, `match_ip`, `replace_ip`,
  `bind_nic`, `nic_name_filter`, and the embedded Chinese log strings did not
  identify a public upstream project from this environment.
- VirusTotal/Hybrid Analysis/Triage pages were reachable only as web UI or were
  blocked/rate-limited without API/authenticated access, so no authoritative
  public reputation result was obtained.

Recommendation: remove `Ak.dll` from normal Astral-ng packaging unless a known
Windows runtime feature is proven to require it. If it is intentionally needed,
document the matching `kl.toml` format and the process that is supposed to load
it; do not ship it silently as a generic runtime dependency.

## Notes for maintenance

- Do not replace these files with different architectures. The top-level bundle
  is x86-64 only.
- If Windows setup builds need FakeTCP support, add `WinDivert64.sys` to the
  generated Inno Setup `[Files]` list. It is currently only guaranteed to be in
  the zip artifact.
- Prefer updating EasyTier's `third_party` files and this directory together so
  build-time and runtime copies stay aligned.
- `Packet.lib` should not be required in an end-user runtime directory. Keeping
  it here is harmless but noisy in the zip artifact.
